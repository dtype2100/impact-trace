# 금융 포지셔닝 UI 명확화

Status: 사용자 설계 승인 반영  
Date: 2026-07-26  
Scope: `/Users/jinlee/resume/regulation-impact-trace`

## 목적

화면이 어느 산업의 누구를 위한 도구인지 드러내지 못하는 문제를 해결한다. 데이터는 이미 EU 금융 규제 DORA 조항으로만 구성돼 있으므로, 화면을 금융 단일 포지셔닝으로 명확히 맞춘다.

완료된 화면은 설명 없이 처음 열어본 사람이 1분 안에 다음을 파악할 수 있어야 한다.

```text
누구를 위한 도구인가
  → 어떤 규제를 다루는가
  → 무엇을 자동화하고 무엇을 사람이 결정하는가
  → 지금 보고 있는 것이 실제 모델 결과인가 고정 데이터인가
```

## 현재 문제

- 제목과 설명이 `Regulation Impact Trace`, `Regulatory operations`로 산업 중립이라 대상 사용자가 드러나지 않는다.
- 데이터는 `DORA-ART-5/6/11/17/28/30` 여섯 조항으로 전부 금융 규제인데 화면에 DORA도 금융도 등장하지 않는다.
- 검색 방식, HITL 구조, 배포 모드 같은 설계 의도가 화면에 전혀 설명되지 않는다.
- `FIXTURE` 배지만 있고 그 의미가 없어, 고정 데이터로 동작한다는 사실이 전달되지 않는다.
- 근거 목록이 `id`와 `title`만 표시하고 응답에 있는 `article`과 `obligation`을 버린다.
- 그래프 경로가 `Clause:DORA-ART-17` 형태의 원문 문자열이라 네 단계 연결 관계로 읽히지 않는다.
- 예시 질문이 하나뿐이라 코퍼스가 무엇을 담고 있는지 알 수 없다.
- 평가 테이블이 `baseline`, `candidate`를 그대로 노출해 두 방법의 차이를 알 수 없다.
- 첫 진입 시 `데이터 동기화`를 눌러야 분석이 열리는데, 그 단계가 왜 필요한지 안내가 없다.

## 포지셔닝 결정

### 결정

금융으로 확정한다. 제조 확장 여지를 화면에 암시하지 않는다.

한 문장 정의:

> EU 금융 규제 DORA 조항을 금융회사의 업무 절차와 증빙 요구사항으로 번역하고, 사람이 승인한 결정만 감사 기록에 남기는 GraphRAG 워크벤치

대상 사용자: 금융회사 ICT 리스크 · 준법감시 담당자

### 근거

DORA는 금융기관과 그 ICT 제3자 공급자에게 적용되는 금융권 전용 규제다. 제조업은 적용 대상이 아니므로 제조 포지셔닝은 `data/regulations.json`과 `data/evaluation.json`을 전면 교체해야 하고, 그 경우 프로젝트의 전제 자체가 바뀐다. 현재 코퍼스를 유지하면 데이터 작업 없이 화면만으로 포지셔닝을 확정할 수 있다.

### 검토한 대안

1. 제조로 전환: 중대재해처벌법·산업안전보건법 등으로 코퍼스를 교체한다. 작업량이 크고 기존 DORA 기반 서사와 평가 질문셋을 버리게 되어 선택하지 않았다.
2. 금융 코어 + 제조 확장 여지 암시: 산업 전환이 가능한 구조임을 화면에서 시사한다. 애매함이 일부 남아 목적과 충돌하므로 선택하지 않았다.
3. 금융 단일 확정: 데이터와 화면이 일치하고 작업이 카피·렌더링에 국한되어 선택했다.

## 변경 항목

### A. 헤더 재작성

`app/index.html`의 `.operations-bar` 좌측 블록을 교체한다.

- eyebrow: `금융 ICT 리스크 · DORA 대응`
- `h1`: `Regulation Impact Trace` (제품명이므로 유지)
- lede: `EU 금융 규제 DORA 조항을 금융회사의 업무 절차와 증빙 요구사항으로 옮기고, 사람이 승인한 결정만 감사 기록에 남깁니다.`
- 대상 사용자 한 줄 추가: `대상: 금융회사 ICT 리스크 · 준법감시 담당자`

### B. 소개 블록 신설

`.operations-bar` 아래, `#live-status` 위에 `<section class="brief">`를 추가한다. 제목은 `이 파일럿이 보여주는 것`이며 네 항목을 `<dl>`로 구성한다.

| 용어 | 설명 |
|---|---|
| 규제 코퍼스 | 공개 DORA 조항 6건(Article 5·6·11·17·28·30)을 조항 → 의무 → 절차 → 증빙으로 구조화합니다. |
| 검색 | 키워드·벡터·그래프 후보를 RRF로 결합하고 재순위 API로 좁힙니다. |
| 사람의 결정 | 시스템은 조치 초안까지만 만들고, 승인과 반려는 사람이 합니다. |
| 배포 | 자격증명 없이 동작하는 fixture 모드와 폐쇄망 연동용 live 모드를 같은 API로 제공합니다. |

이 블록은 접이식으로 만들지 않고 항상 노출한다.

### C. 모드 배지 보조 문구

`#mode-badge` 옆에 `#mode-note` 요소를 추가하고, `loadHealth()`에서 모드별 문구를 설정한다.

| 모드 | 문구 |
|---|---|
| `fixture` | 고정 데이터로 동작 · LLM 호출 없음 · 결과 재현 가능 |
| `live` | 외부 생성·임베딩·재순위 API와 Neo4j에 연결됨 |
| `misconfigured` | 환경변수 여섯 개가 모두 필요합니다 |

fixture 모드임을 숨기지 않는다. 자격증명 없이 재현 가능한 데모를 설계했다는 사실을 그대로 보여준다.

### D. 근거 목록 정보 보강

`app.js`의 `renderTrace()`가 현재 `${item.id}: ${item.title}`만 표시한다. 다음으로 바꾼다.

- 링크 텍스트: `${item.article} · ${item.title}`
- 링크 아래 `<p class="evidence-obligation">`에 `item.obligation` 표시

`article` 또는 `obligation`이 없으면 각각 `item.id`와 빈 문자열로 폴백한다. 두 필드는 fixture 데이터에 존재하고, live 모드도 동기화 시 `SET c += $record`로 원본 필드를 보존하므로 동일하게 반환된다.

### E. 추적 경로 시각화

`graph_paths[0]`의 각 항목은 `Clause:DORA-ART-17` 형태다. 첫 콜론을 기준으로 분리해 단계명과 값을 별도 요소로 렌더링한다.

- `<span class="trace-step-label">`: 콜론 앞 (`Clause`, `Obligation`, `Process`, `Evidence`)
- `<span class="trace-step-value">`: 콜론 뒤

콜론이 없으면 전체를 값으로 처리하고 단계명은 비운다. 서버 응답 형식은 바꾸지 않는다.

### F. 예시 질문 칩 3개

`#sample-button` 하나를 칩 세 개로 교체한다.

| 칩 라벨 | 입력되는 질문 | 의도 조항 |
|---|---|---|
| 사고 관리 | ICT 사고 관리 절차와 증빙은 무엇인가? | DORA-ART-17 |
| 제3자 리스크 | ICT 제3자 공급자 위험은 어떻게 관리하는가? | DORA-ART-28 |
| 업무연속성 | 업무연속성과 백업 복구 시험 요구사항은 무엇인가? | DORA-ART-11 |

각 칩은 `#query-input`에 질문을 채우기만 하고 자동 제출하지 않는다. 검증 중 의도한 조항이 상위 5건에 들지 않으면 검색 로직이 아니라 질문 문구를 조정한다.

### G. 평가 테이블 라벨

- 행 라벨: `baseline` → `제목·요약만 검색`, `candidate` → `그래프 필드 확장 검색`
- `<caption>`: `검색 평가 비교 — 고정 질문셋 기준의 결정론적 검색 품질이며 모델 성능이 아닙니다`

`renderEvaluation()`은 계속 `baseline`, `candidate` 키로 응답을 읽되 표시 라벨만 매핑한다.

### H. 첫 진입 동선 안내

- 버튼 라벨: `데이터 동기화` → `① 규제 데이터 색인`
- `#sync-state` 초기 문구: `동기화 전` → `색인 전 · 먼저 실행하세요`
- 버튼 아래 한 줄 추가: `조항을 검색 색인에 올립니다. live 모드에서는 Neo4j에 동기화합니다.`

색인 단계를 자동 실행으로 바꾸지 않는다. 데이터 동기화 단계 자체가 이 프로젝트가 보여주려는 운영 서사의 일부다.

## 변경 범위

| 파일 | 변경 |
|---|---|
| `app/index.html` | 헤더 카피, 소개 블록 신설, 모드 노트 요소, 예시 칩 3개, 평가 캡션, 동기화 안내 |
| `app/static/app.js` | `renderTrace`, `renderEvaluation`, `loadHealth` 수정, 칩 이벤트 핸들러 |
| `app/static/styles.css` | 소개 블록, 칩, 경로 단계, 모드 노트, 근거 의무 문구 스타일 |

백엔드(`app/main.py`, `app/api/*`, `app/services/*`), 데이터(`data/*`), 기존 테스트는 변경하지 않는다.

## 범위 밖 관찰

`app/services/live.py:45`의 Cypher가 `c {.*}`로 Clause 노드의 모든 속성을 반환한다. 동기화 시 `c.embedding`을 저장하므로 live 모드 응답에 임베딩 벡터가 함께 실려 브라우저까지 전달된다. 이번 작업 범위가 아니며 별도로 다룬다.

## 테스트 전략

기존 자동 테스트는 구조와 아키텍처만 검증하고 UI 카피를 검증하지 않는다. `tests/test_app.py:212-219`는 정적 자산 연결을, `tests/test_app.py:260-261`은 `innerHTML` 미사용을 확인한다. `tests/test_structure.py:117-130`은 README의 환경변수 문서를 검증하므로 이번 작업에서 README를 수정하지 않는다.

자동 테스트:

- 기존 테스트 전체가 그대로 통과한다.
- `innerHTML`을 사용하지 않는다.

수동 브라우저 검증:

- 색인 → 분석 → 승인 → 감사 → 평가 전체 흐름
- 예시 칩 세 개가 각각 의도한 조항을 상위 5건 안에 포함시키는지 확인
- fixture 배지 보조 문구 노출
- 근거 목록에 `article`과 `obligation` 표시
- 추적 경로가 네 단계 연결 관계로 읽히는지 확인
- 320px 폭에서 가로 스크롤 없음
- 브라우저 콘솔 오류 없음

- 첫 화면에서 대상 사용자와 규제 종류가 드러난다.

- 추적 경로의 단계명과 값이 시각적으로 구분된다.
