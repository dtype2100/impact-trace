# Regulation Impact Trace 웹 UI 재설계

Date: 2026-07-25

## 목적

기능 검증 패널처럼 보이는 현재 화면을 규정 담당자가 순서대로 사용할 수 있는 전문적인 업무 도구로 바꾼다. 기존 FastAPI API, GraphRAG 검색, HITL 승인, 감사 기록과 평가 동작은 유지한다.

완료된 화면에서 사용자는 별도 `curl` 없이 다음 흐름을 이해하고 실행할 수 있어야 한다.

```text
데이터 동기화
  → 규정 질문
  → Clause → Obligation → Process → Evidence 확인
  → 조치 초안 승인 또는 반려
  → 감사 기록과 검색 평가 확인
```

## 현재 문제

- HTML, CSS와 JavaScript가 `app/index.html` 한 파일에 압축되어 관심사가 섞여 있다.
- 분석, 근거, 검토와 평가가 같은 무게의 카드로 나열돼 시작점과 작업 순서가 불명확하다.
- 동기화 API가 화면에 없어 사용자가 별도 명령을 실행해야 한다.
- 그래프 경로가 연결 관계가 아닌 문자열 묶음으로 보인다.
- 로딩, 빈 결과, 오류와 결정 완료 상태가 충분히 구분되지 않는다.
- 소스, 감사 기록과 평가 지표의 정보 밀도와 시각적 위계가 약하다.

## 선택한 접근

빌드 단계 없는 Vanilla JavaScript를 유지하면서 HTML, CSS와 동작을 분리한다.

```text
app/
├── main.py
├── services.py
├── index.html
└── static/
    ├── styles.css
    └── app.js
```

- `main.py`: 기존 API와 정적 파일 제공
- `services.py`: 기존 검색·동기화·승인 업무 로직
- `index.html`: 문서 구조, 콘텐츠 순서와 접근성 마크업
- `styles.css`: 디자인 토큰, 레이아웃, 컴포넌트 상태와 반응형 규칙
- `app.js`: API 클라이언트, 화면 상태, DOM 렌더링과 이벤트 처리

프로젝트 규모상 `api.js`, `store.js`, 컴포넌트 파일을 추가로 만들지 않는다. 한 JavaScript 모듈 안에서 API, 상태, 렌더링과 이벤트 영역을 함수 단위로 구분한다.

### 검토한 대안

1. React/Vite: 컴포넌트 구조는 익숙하지만 빌드와 의존성이 추가되어 당일 파일럿에는 과하다.
2. Jinja 서버 렌더링: 초기 화면은 단순하지만 분석·승인·감사 갱신 같은 상호작용에 부분 렌더링 복잡성이 생긴다.
3. Vanilla JS 관심사 분리: 현재 API를 유지하고 추가 도구 없이 구조와 UX를 개선할 수 있어 선택했다.

## 정보 구조

데스크톱에서는 주 작업과 검토 작업을 비대칭 2열로 구성하고, 모바일에서는 한 열의 작업 순서로 바꾼다.

```text
┌──────────────────────────────────────────────────────────┐
│ 제품 설명                    모드 · 동기화 상태 · 동기화 │
├───────────────────────────────────┬──────────────────────┤
│ 질문 입력                         │ 조치 검토            │
│ 근거 기반 답변                    │ 승인 / 반려          │
│                                   │                      │
│ Clause → Obligation → Process     │ 최근 감사 기록       │
│                    → Evidence      │                      │
│ 공식 출처                         │                      │
├───────────────────────────────────┴──────────────────────┤
│ 검색 평가: baseline ↔ candidate                         │
└──────────────────────────────────────────────────────────┘
```

### 영역

1. **상단 운영 바**
   - 제품명과 한 문장 설명
   - `FIXTURE`, `LIVE`, `MISCONFIGURED` 모드 배지
   - 동기화 상태, 마지막 run ID와 `데이터 동기화` 버튼
2. **질문과 분석**
   - 예시 질문 버튼
   - 질문 입력과 `영향 분석` 버튼
   - 근거 부족 시 다음 행동을 안내하는 빈 상태
3. **영향 추적**
   - 답변 요약
   - 첫 번째 근거 경로를 네 단계 연결선으로 표시
   - 공식 출처 목록
4. **조치 검토**
   - 분석 전에는 비활성 안내
   - 초안, 결정 사유, 승인과 반려
   - 결정 후 버튼을 비활성화하고 감사 기록 갱신
5. **평가와 감사**
   - baseline과 candidate의 Recall@5·MRR 비교
   - 결정, 사유와 대상 draft를 시간 순서로 표시

## 화면 상태

전역 프레임워크 대신 작은 상태 객체를 사용한다.

```text
idle
  → syncing
  → ready
  → analyzing
  → review-ready
  → decided
```

필수 상태:

- `mode`: fixture, live 또는 misconfigured
- `phase`: 현재 작업 단계
- `draft`: 현재 검토 가능한 초안 또는 `null`
- `syncRun`: 마지막 동기화 결과 또는 `null`

각 비동기 작업은 시작 시 관련 버튼을 비활성화하고, 종료 시 성공 또는 오류 메시지를 해당 영역과 전역 `aria-live` 상태에 표시한다. 동기화 실패는 분석 결과를 지우지 않고 재시도를 안내한다. 근거가 없으면 검토 초안을 만들지 않는다.

## 시각 시스템

규정 문서, 감사 기록과 업무 경로에 맞는 정밀한 운영 화면을 지향한다.

### 색상

- `Ink` `#102A43`: 제목과 핵심 본문
- `Slate` `#52667A`: 보조 설명
- `Canvas` `#F4F7FA`: 페이지 배경
- `Surface` `#FFFFFF`: 작업 표면
- `Action Blue` `#2563EB`: 주요 동작과 현재 단계
- `Evidence Teal` `#0F766E`: 근거와 정상 상태
- `Decision Amber` `#A15C00`: 주의와 반려
- `Rule` `#D8E2EA`: 구분선

### 글꼴

- 본문과 제목: 시스템 한국어 산세리프 스택
- 조항 ID, run ID와 지표: 시스템 고정폭 스택

외부 웹폰트 의존성은 추가하지 않는다. 제목 크기보다 간격, 굵기와 구분선을 이용해 위계를 만든다.

### 대표 요소

이 화면의 시각적 서명은 `Clause → Obligation → Process → Evidence` 경로다. 각 노드는 다른 색상 카드가 아니라 하나의 연속된 증거선으로 표현하고, 작은 화면에서는 세로 타임라인으로 변환한다.

그라데이션, 장식용 일러스트, 챗봇 말풍선, 과도한 그림자와 애니메이션은 사용하지 않는다.

## 상호작용과 데이터 흐름

1. 페이지가 열리면 `/healthz`와 `/api/audit`를 병렬로 읽는다.
2. 사용자가 동기화하면 `POST /api/sync`에 안정적인 기본 idempotency key를 보낸다.
3. 동기화 성공 후 분석 버튼을 활성화한다. Fixture 모드에서는 페이지 새로고침 뒤에도 다시 동기화할 수 있다.
4. 질문 제출 시 `POST /api/analyze` 결과로 답변, 경로, 출처와 draft를 함께 렌더링한다.
5. 승인 또는 반려 시 사유를 검증한 뒤 `POST /api/reviews`를 호출한다.
6. 결정 성공 후 draft를 잠그고 `/api/audit`를 다시 읽는다.
7. 평가 버튼은 `POST /api/evaluation/run` 결과를 비교 테이블에 표시한다.

기존 API 계약과 응답 구조는 변경하지 않는다.

## 보안과 접근성

- API 응답은 `textContent`, `createElement`와 안전한 URL 검증으로만 표시한다.
- `innerHTML`, 인라인 이벤트 핸들러와 동적 코드 실행을 사용하지 않는다.
- 모든 입력에 명시적 `label`을 연결한다.
- 키보드 포커스를 눈에 띄게 표시한다.
- 상태 변화는 `aria-live`로 알린다.
- 색상만으로 상태를 표현하지 않는다.
- 모션이 필요한 경우 `prefers-reduced-motion`을 존중한다.
- 모바일 최소 320px에서 가로 스크롤 없이 작업할 수 있어야 한다.

## 테스트 전략

자동 테스트:

- `/static/styles.css`와 `/static/app.js`가 제공된다.
- HTML이 외부 CSS와 모듈 JavaScript를 참조한다.
- 동기화, 분석, 검토와 평가 컨트롤이 존재한다.
- API 콘텐츠 렌더링에 `innerHTML`을 사용하지 않는다.
- 기존 fixture와 live 서비스 회귀 테스트 22개가 유지된다.

수동 브라우저 검증:

- 데스크톱과 모바일 폭에서 레이아웃 확인
- 동기화 → 분석 → 승인 → 감사 → 평가 전체 흐름
- 로딩 중 중복 실행 방지
- 근거 부족, 입력 오류와 API 오류 상태
- 키보드 탭 순서와 포커스 표시
- 브라우저 콘솔 오류 없음

## 완료 조건

- 사용자가 화면만 보고 시작점과 다음 단계를 이해할 수 있다.
- 별도 명령 없이 UI에서 동기화부터 평가까지 실행할 수 있다.
- HTML, CSS와 JavaScript가 역할에 따라 분리된다.
- 첫 번째 그래프 경로가 네 단계의 연결 관계로 인식된다.
- 데스크톱과 모바일에서 핵심 작업이 끊기지 않는다.
- 기존 API와 모델·검색·승인 로직은 변경되지 않는다.
- 자동 테스트와 fixture HTTP 흐름이 통과한다.
- 실제 브라우저 검증 결과와 제한 사항을 최종 보고한다.
